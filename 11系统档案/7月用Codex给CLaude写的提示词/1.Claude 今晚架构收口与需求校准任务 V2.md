### 第一步：先测量，不准凭感觉优化

修改前选择至少 20 个真实任务类型进行只读基线测量：

- 普通咨询
- 记录一句灵感
- 读取一个文件并整理
- 账号诊断
- 选题
- 大纲
- 单篇写稿
- 拍摄版
- 完整生产链
- 任务中断后恢复

每个任务记录：

- 用户发出请求到首次出现反馈的时间
- 首个有效结果出现时间
- 完整完成时间
- 模型调用次数
- 工具调用次数
- 文件读取数量与总字节
- 写入次数
- 重试次数
- Token 估算
- 是否发生压缩
- 是否扫描全部 sessions
- 是否重复读取同一个文件
- 是否需要用户说“继续”

必须输出耗时瀑布：

路由耗时 → 读取耗时 → 模型等待 → 工具执行 → 校验 → 写入 → 最终回复。

没有基线数据，不允许宣布“已提速”。

### 第二步：建立最短执行路径

普通任务默认执行：

识别任务 → 读取最小必要资料 → 一次生成 → 本地自动修复 → 一次集中校验 → 落盘 → 返回结果。

禁止默认执行：

识别 → 分析 → 建计划 → 再确认 → 多轮自审 → 多个子代理 → 多次评分 → 多次重写 → 多次校验 → 用户继续确认。

任务分为三条通道：

#### 极速通道

适用于：

- 记录灵感
- 查状态
- 读取单个文件
- 简单整理
- 改名、格式、提取信息
- 已有稿件的小修改

要求：

- 优先本地执行。
- 不调用模型就能做的，绝不调用模型。
- 最多一次模型调用。
- 不启动子会话。
- 不加载完整技能包。
- 不要求用户确认内部步骤。

#### 标准通道

适用于：

- 账号诊断
- 选题
- 大纲
- 单篇写稿
- 拍摄版

要求：

- 一个阶段最多一次主生成＋一次必要修订。
- 所有机械检查合并成一次。
- 最多重试一次。
- 重试仍失败立即停止并说清原因，禁止换工具继续撞墙。
- 只挂载本阶段需要的规则与素材片段。

#### 深度通道

只适用于：

- 批量内容生产
- 跨大量素材分析
- 系统审计
- 用户明确要求深度推演的任务

深度通道也不得自动堆叠子代理。必须先证明拆会话比单会话更快、更稳定，才能启用。

### 第三步：减少模型工作

- 队列状态判断
- 已完成任务过滤
- Token 粗估
- 日志聚合
- 内容是否发生变化

模型只负责：

- 判断
- 诊断
- 角度选择
- 大纲设计
- 写作
- 声画推演
- 复盘建议

禁止用昂贵的模型调用处理代码能够百分之百确定的事情。

### 第四步：消灭重复读取和全量扫描

当前 sessions 目录约 769MB、2237 个 JSONL，禁止在用户请求期间重复全量扫描。

要求：

- Dashboard 读取缓存后的聚合结果，不直接扫描全部会话。
- backup、coaching harvest、健康统计等进入后台任务，不得阻塞用户请求。

- 同一份规则和素材不得被多个环节重复整读。
- 对超大文件只取当前任务所需段落。
- 后台任务限制并发和磁盘读取预算。
- 用户正在生产时，低优先级统计任务自动让路。

### 第五步：合并门禁，不削弱门禁

安全门禁必须保留，但不能一条一条让模型反复撞。

正确方式：

1. 生成前一次性告诉模型本轮所有必要约束。
2. 生成后本地代码一次性完成全部检查。
3. 能自动修的统一修完。
4. 不能自动修的错误一次性完整返回。
5. 每个产物最多重新生成一次。
6. 第二次仍失败就停止，禁止第三次换姿势重试。

禁止出现：

- 改一个问题、重新运行、再发现下一个问题。
- 同一篇稿连续写入十几次。
- 每个门禁分别触发一次模型重试。
- 校验失败后重新执行已经完成的上游阶段。

### 第六步：控制交互次数

用户只为真正需要人判断的事情介入。

写稿流程默认只保留一个人工决策点：

- 选择角度 A/B/C。

以下步骤系统应自动完成：

- 路由
- 读取资料
- 建最小选题卡
- 生成大纲
- 格式修复
- 事实检查
- 落盘
- 状态更新
- 继续下一阶段

除非发现事实缺失、安全风险或多个方向会产生完全不同结果，否则不许频繁问用户“是否继续”。

用户说一次“继续”，系统必须跑到下一个真正需要用户判断的节点，不能每完成一个内部步骤就停下来汇报。

### 第七步：性能预算

先测基线，再达到以下目标：

- 请求发出后 2 秒内必须出现可见反馈，不能像死机。
- 极速通道本地任务 p95 不超过 5 秒。
- 标准 AI 任务首个有效结果 p95 不超过 15 秒；若模型本身无法达到，必须显示真实进度。
- 相同任务修改后总耗时 p50、p95 至少降低 40%。
- 简单任务模型调用不超过 1 次。
- 标准阶段模型调用原则上不超过 2 次。
- 单个工具错误最多重试 1 次。
- 重复文件读取量下降至少 70%。
- 用户请求期间不得全量扫描 sessions。
- 后台任务不得抢占生产任务。
- 速度提升后，跨用户泄漏仍为 0，事实回归仍为 0，现有测试仍为 0 回归。

如果受 DeepSeek 服务端速度影响达不到绝对时间，必须把：

- 模型等待时间
- 小龙自身处理时间

分开统计。不能把小龙架构浪费的时间都归因于模型。

### 第八步：T2 多会话方案暂缓上线

“一棒一个隔离会话”不天然等于更快。

每次新建会话都会产生：

- 启动成本
- 固定提示词成本
- 文件重新读取
- 交接卡生成
- 状态同步
- 故障面增加

T2 必须先与当前单会话方案做同一任务 A/B 压测。

只有同时满足以下条件才能启用：

- 完整任务总耗时更低。
- 模型调用次数没有明显增加。
- 第一次有效结果更快。
- 上下文没有溢出。
- 质量没有下降。
- 中断恢复成功。
- 没有重复产物。
- 没有跨用户串号。

否则保留“一个任务一个干净工作会话”，不要机械地“一棒一个会话”。

### 最终性能交付报告

最终必须单独提供：

1. 修改前后 p50、p95 耗时。
2. 修改前后模型调用次数。
3. 修改前后工具调用次数。
4. 修改前后读取文件数量和字节数。
5. 修改前后重试次数。
6. 最慢的三个环节。
7. 已消除的等待。
8. 仍属于 DeepSeek 服务端的等待。
9. 为了提速有没有牺牲质量或安全。
10. 用户现在完成同一个任务，少等了多少时间、少点了几次“继续”。

禁止用“理论上更快”“做了缓存”“减少 Token”代替真实测速。

# 超级工厂重构与优化指南（v6 稳定期版）

> 出具人：Claude（教练员）· 2026-07-19
> 依据：当日全量实测——28 个技能逐个过堂（五路只读盘点，70 次工具调用，零抽样）+ openclaw.json 现值核验 + workspace git 现状。不是纸上推演。

## 0. 先纠三个前提（这份需求提示词是小龙写的，三处与实测不符）

1. **"42 个 Skill" → 实为 28 个。** `skills/` 目录 31 个条目，减去 `_backups`、`_共享资源`、`_历史与私有追溯` 三个非技能目录，真实技能 28 个。42 是把原生工具、插件、已归档件混着数的。清单类结论必须先枚举全集——这次枚举完了。
2. **"Token 撑爆是因为把流程逻辑当 System Prompt 硬塞"——已证伪。** 07-18 实测 `context.compiled`：systemPrompt 只有 **105 字符**，tools 32k，messages 116k。OpenClaw 根本不是"把 skill 塞进 system prompt"的架构（Gemini 同款错误理论）。撑爆真凶四件套（全部有日志实锤）：①盲打分子代理漏 `context:isolated` 继承 116k 主会话历史（07-18 已修）；②工具返回值失控——一次搜索甩回 100 条路径、toolResult 占 context 56%；③语音整理下游全回 pro 反复读大文件（07-18 已修）；④平台 CJK token 估算缺陷（issue #103930，中文按英文 chars/4 低估，OPEN 未修）。
3. **"重构拆分"这个方向本身就是刚翻过的车。** Codex v7 大重构把知识包砍 53-94%，AI 味变重，07-17 回滚 v6 才把质量找回来；07-18 已定稳定期方针。所以本指南 = **小刀清单，不是大改蓝图**。任何一条动作都以"可逆、带备份、不动手艺文本"为前提。

## 一、Subagent 拆分：不设常驻编制，用"主脑 + 分身"三角

**"研发 Agent / 生产 Agent / 质检 Agent"常驻分层在 OpenClaw 上落不了地，也不该落。** 实测约束：

- `sessions_spawn` 支持 `model=` 覆盖 + `context:isolated` + `cleanup:delete`，`maxSpawnDepth:1`（分身是叶子，结构上不可能递归）。
- **per-skill 指定模型不支持**（frontmatter 只认 name/description/disable-model-invocation，07-11 验过）。
- 分身多了不省 token——每个分身照样吃 API 预算，撑爆的根因也不在"一个脑干了太多活"。

**已验证的正确形态（三角）：**

| 角色 | 承担 | 现状 |
|---|---|---|
| **pro 主脑** | 全部判断活：评级、文风、审美、拍板前整理 | 常驻 |
| **flash 跑腿分身** | 读大料、清洗、采集聚合，只回小料单不回全文 | yuyin 07-13 真实验证；fanwen §2.0 读料工人 07-18 落地；weekly-review §4a 已写入 |
| **isolated 盲打分** | Channel B 独立评分，防主会话历史污染 | 07-18 冉总卡死事故后 `context:isolated + cleanup:delete` 焊死 + 降级兜底 |

**spawn 铁律（写死，无例外）：** 凡 `sessions_spawn` 必带 `context:isolated` + `cleanup:delete`——07-18 冉总第 20 稿的"Auto-compaction could not recover"就是漏了这一个参数：分身继承 116k 历史 → precheck 拒收 → 主会话死等。

**真正治撑爆的四件事：** ①盲打分 isolated（已修）；②语音下游卸载（已修）；③整读改定向（本指南阶段 1 主菜）；④ **恢复被回滚卷走的 `session.reset=daily@4h` + compaction 调优值**——现值已退回平台默认 35000/20000，冉总式"贴线蹦迪"会回来。第④件是拍板项。

## 二、形态鉴定：三分法 + 28 技能判定表

**先回答"该不该写成 JSON Schema 工具"：基本不该。** OpenClaw 的"工具形态"就是 exec 脚本——判据不是"像不像函数"，而是**输出是否确定性可校验**。四条分派规则：

1. **判断活留提示词**（评级/文风/审美/归因）——这是 DeepSeek 该干的，也只有 prompt 能承载。
2. **机械活交脚本**（排版/编号/文件名/禁词/对账/坐标算术）——07-05 十二轮实测：排版类随机病 1/3 失败率，赌不住模型自觉。fanwen_format_lint 是样板。
3. **力气活派 flash 分身**（读大文件/清洗/多文件采集）——只回 digest，pro 不碰原文。
4. **手艺知识文本永不蒸馏**（作战包/评分尺/例句/柯哥原话）——v7 把 fanwen 作战包 10515B 压成 676B 的事故不许重演。整读、原位、原文。

## 三、五棒交接硬闸：闸已经够多了，缺的是物理层

**先泼冷水：不要再造闸。** 五棒交接协议（18670B）现有闸清单——三确认点（选题拍板/方向拍板/终稿验收）、账号路由硬闸、无 dagang 禁写稿、BLOCKED 只出拍摄引导版、跳棒检测（进 fanwen 前强制 ls dagang 粗坯）、写稿触发词三步自检、下棒必读清单、编号污染急停、单会话上下文硬闸、72h 新硬闸孵化期。**该有的全有了。**

问题在协议 §156 自己写的那句话：**SKILL 层规则只能提示、无法强制**——上下文一压缩，规则文本先被吃掉，闸就跳了。往 SKILL 再堆规则 = 更吃 context = 更容易被跳，负反馈。

**结论三条：**

1. **物理闸才是 100%。** 曾经的物理层是 superfactory-guard（无大纲禁写/独立裁判 80 分闸/judge-approved 防偷换/覆盖前备份，回滚前一天拦截 22 次），07-17 随回滚离线。代码还在 `extensions/`，`openclaw.json.bak`（07-17 15:39）三处配置齐全——**加回 + 重启即复活**。要不要加回是柯哥的拍板项（可只加安全子集：防覆盖 + 无大纲禁写，裁判闸缓上）。
2. **交接走磁盘，不走上下文。** "用 XML/JSON 标记让上下游 100% 不掉链子"是幻觉——上下文里的任何标记都会被压缩吃掉。现行架构已经答对了：交接卡/ACTIVE.md/dagang 粗坯文件**落盘即总线**，下一棒从磁盘读，压缩杀不掉磁盘。要强化的只是"读写这些卡走脚本"（append/摘要），别让 44KB 的队列文件整个灌回上下文。
3. **提示词层结构化输出只能降概率，脚本校验才能兜底。** 给 DeepSeek 的交接卡格式已统一（任务链 ID/本棒/状态/上游文件/递下一棒的话）；真正保真靠的是 lint 类脚本对产物做确定性断言，FAIL 拦截。"100%"三个字只存在于 fail-closed 的物理闸里。

## 一、柯哥四条拍板(写死,不许改也不许猜)

1. **操盘手 = 只审不代管**:operator 只能**只读**查看绑定 IP 的内容 + 提交朱批/批准/打回,**绝不能替 IP 写 workspace/跑五棒**。这条同时守住"用户数据不互串"红线——operator 对 IP 数据只读。
2. **绑定 = 双向确认**:IP 发起绑定 → operator 接受后才生效(active);任一方可解绑。杜绝 IP 单向声明。
3. **操盘手 = 要 admin 审批**:关闭自助注册 operator;必须走"申请 → admin 批准 → 授予 operator 角色"。呼应柯哥"严把质量"。
4. **封号 = 触发退款 + 社群内容保留**:admin 可封禁用户;封号连带作废其分销佣金、登记其未成熟订单退款(仅状态登记,不碰真实转账);**该用户的社群帖子保留**(仅标记作者已封,不删)。

## 二、我(Claude)对"其余你来定"部分的补充决策

- **朱批粒度**:operator 对「灵感」和「文稿」两类都能审(灵感阶段给方向,文稿阶段把关)。verdict 三态:批准 / 要求修改 / 仅批注。
- **绑定数量**:一个 IP 可绑多个 operator?→ **先限 1 个**(1 IP : 1 operator),简单可控,后续要多对多再放开。operator 可管多个 IP。
- **封禁分级**:两级——SUSPENDED(停用,可解封,token 失效但数据留)、BANNED(封禁,同 SUSPENDED + 触发退款钩子)。删除用户**不做**(红线:不物理删,最多软删标记,本期不做)。
- **退款登记范围**:封号只作废"该用户作为分销员赚的未成熟(PENDING)佣金";其作为买家的订单退款**只登记待处理**,实际退款走线下(不碰真实转账红线)。
- **operator 只读通道的数据面**:operator 通过新端点只读拉取绑定 IP 的 workspace 快照,**不 union 进自己的 workspace**(避免污染自己数据),独立展示。

### F-R1 · 绑定系统(双向确认)· 1.5 天 · 依赖决策②
**数据模型** 新 `bff/src/repo/operatorBindings.ts`:
```
Binding = { id, ipUserId, operatorId, status: 'pending'|'active'|'revoked',
            createdAt, respondedAt?, revokedAt?, revokedBy? }
```
存 `bff/data/bindings/bindings.jsonl`(append + rewrite),一 IP 最多一条 active(决策补充:1:1)。
**后端路由** 新 `bff/src/routes/bindings.ts`(requireAuth):
- `POST /api/bindings` (IP) body `{operatorId}`:校验 operatorId 是真实 active operator;若 IP 已有 active/pending 绑定则拒;建 pending;给 operator 发 notification(collaboration 类型,href 指向待确认)
- `POST /api/bindings/:id/respond` (operator) body `{accept:boolean}`:仅该 binding 的 operator 可操作;accept→active,拒→revoked;给 IP 发 notification
- `POST /api/bindings/:id/revoke` (IP 或 operator):active→revoked + 通知对方
- `GET /api/bindings/mine`:IP 返回我的操盘手(含 pending),operator 返回待确认 + 在管 IP 列表
**前端**:
- `src/services/bindingService.ts`:上述端点封装
- `src/pages/AuthPage.tsx`:注册绑定改成"发起 pending"(不再假装已绑定;删 setTimeout 假活),文案改"已向 X 发送绑定请求,等待接受"
- `src/pages/OperatorHome.tsx`:顶部"待确认绑定"卡片,接受/拒绝按钮
- `src/pages/Profile.tsx`:"我的操盘手"区,显示状态 + 解绑
**验收**:IP-A 发起绑定 operator-X → op-X 的 OperatorHome 出现待确认 → 接受 → 双方状态 active;op-X 拒绝则 revoked;任一方解绑生效;全程有通知。

### F-R2 · operator 只读 IP 内容 + 朱批闭环(只审)· 2 天 · 依赖 F-R1 + 决策①
**只读通道** `bff/src/routes/operator.ts`(requireAuth,role=operator):
- `GET /api/operator/ips`:我在管(active 绑定)的 IP 列表 + 每个 IP 的账号/画像摘要
- `GET /api/operator/ips/:ipUserId/workspace`:**只读**返回该 IP 的 workspace 快照(灵感/文稿),鉴权=存在 active 绑定;**无任何写端点**(守决策①只审)
**朱批存储** 新 `bff/src/repo/reviews.ts`:
```
Review = { id, ipUserId, accountId, targetType:'inspiration'|'script', targetId,
           operatorId, verdict:'approved'|'revision'|'comment', note, createdAt }
```
存 `bff/data/reviews/<ipUserId>.jsonl`(归属 IP)。
**朱批路由** `bff/src/routes/reviews.ts`:
- `POST /api/reviews` (operator,鉴权 active 绑定):写 review + 给 IP 发通知;若 verdict=revision 顺带把该 target 状态置 REVISION_REQUESTED
- `GET /api/reviews?ipUserId=&targetId=`:IP 和绑定 operator 都可读
**前端**:
- `src/services/operatorService.ts`:补 `listManagedIps()` / `getIpWorkspace(ipUserId)` / 提交评审
- `src/pages/OperatorHome.tsx`:**待审队列改对**——聚合在管 IP 里 `inspiration.status==='PENDING_REVIEW'` + `script.status===IN_REVIEW` 两条线(现在只盯了文稿线,漏了灵感朱批);账号卡展示 ownerName + 画像入口(现在只显示账号名)
- `src/pages/InspirationToInterview.tsx` / `ScriptEditor.tsx`:operator 视角只读看 IP 内容 + "批准"/"要求修改"按钮(写 review);IP 视角看到收到的 review;`handleAcceptAndConvert`(继续做成内容)加 isIP 门禁(现在 operator 也能误触)
- 通知:提交审阅/朱批都往对方收件箱写 notification(现在只弹本地 toast,对方永不知道)
**验收**:IP-A 提交灵感待审 → op-X 首页待审队列出现 → op-X 只读看到内容、点"要求修改"写 note → IP-A 收到通知 + 看到 review + 灵感变 REVISION_REQUESTED;op-X 全程无法修改 IP 的 workspace。

### F-R4 · 封禁 + 退款 + 社群保留 · 1.5 天 · 依赖决策④
**后端**:
- `bff/src/routes/admin-users.ts`:加 `PATCH /api/admin/users/:id/status` body `{status:'ACTIVE'|'SUSPENDED'|'BANNED', reason}` → 写 user.status + 审计
- `bff/src/routes/auth.ts` authenticateRequest:对 status=SUSPENDED/BANNED 的用户**拒发/吊销 token**(返 403 ACCOUNT_SUSPENDED),已登录的下次请求即失效

**验收**:admin 封禁 IP-B → IP-B 现有 token 失效(下次请求 403)→ 其 PENDING 佣金 CANCELED + 订单登记 refund_pending + 其社群帖子仍在(标 author_banned);解封后恢复。

## 五、通用红线(所有单)

1. operator 对 IP 数据**只读**,任何写端点都是违规(决策①+数据不互串红线)
2. 鉴权依据 = **active 绑定记录**,不是 workspace 里自证的 operatorId(那是半成品字段,过渡后废弃)
3. userId 只信服务端 token 读的
4. 敏感动作(封禁/审批/标分销/结算)全部 append-only 审计
5. 不碰真实转账;退款只登记状态
6. 原生 alert/confirm 换设计弹窗(全站实际残留 26 处,非 6 处)

回来说为什么压缩会失败。看你的压缩配置，几个硬约束同时作用：

| 参数 | 值 | 含义 |
|---|---|---|
| `maxHistoryShare` | 0.35 | 压缩后历史最多占上下文的 35% |
| `keepRecentTokens` | 20000 | 最近 2 万 token 的原话必须保留 |
| `reserveTokensFloor` | 35000 | 至少留 3.5 万 token 给模型回复 |
| `timeoutSeconds` | 420 | 压缩模型调用最多等 7 分钟 |
| `maxRetries` | 1 | 失败只重试一次 |

以 DeepSeek V4 Pro 的 131k 上下文来算：

- 历史上限：131k × 0.35 ≈ **4.6 万 token**
- 其中最近原话就要占掉 **2 万**
- 留给"压缩摘要"的空间只剩 **2.6 万 token**

**失败通常三种原因**：

1. **量太大压不进去** — 老 session 里大量工具调用、读文件、长输出，压缩模型再怎么摘要也塞不进 2.6 万 token 的预算。
2. **压缩模型调用超时** — 420 秒没返回结果，直接失败。
3. **质量守卫拦截** — `qualityGuard` 开着，压缩产物质量不达标被拒，重试一次还是不行就放弃了。

你那个老 session 应该是累积了太多轮对话 + 大量文件读写，三种里至少中了一种。

**根本上避免**：聊太多之后主动 `/compact` 或 `/new`，别等到自动压缩兜底。自动压缩是最后一道防线，不是日常手段。
